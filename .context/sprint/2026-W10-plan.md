## Sprint Goal

Establish the v4 implementation skeleton without destabilizing v3, and deliver the first end-to-end safe command path foundation:

- side-by-side v4 backend structure
- side-by-side v4 frontend routed shell
- centralized safety config
- initial calibration-aware preflight validation contract
- persistence scaffolding for commands and events
- explicit `poc2` command-consumer scope for real hardware arm/disarm follow-through

This sprint is about laying down the correct architecture and implementation path, not finishing the whole v4 product.

---

By the end of W10, the repo should have:

- a new `poc/v4_mission_control/` backend package scaffold

## Implementation Plan

### Workstream 1: Backend v4 Skeleton

Create the side-by-side v4 backend package under `poc/v4_mission_control/`.

**Target structure**

```text
poc/v4_mission_control/
  app.py
  config.py
  api/
  services/
  models/
  repos/
  schemas/
```

**Expected result**

- v4 backend exists without modifying the runtime behavior of `poc/mission_control_v3.py`
- FastAPI app can boot independently

### Workstream 2: Centralized Safety Config

Implement one shared config source in v4 for:

- `BATTERY_ARM_MIN_PCT = 10`
- `GPS_ARM_MIN_SATS = 4`
- `STALE_TIMEOUT_SEC = 30`
- `COMMAND_ACK_TIMEOUT_SEC = 5`
- `COMMAND_MAX_RETRIES = 3`

**Expected result**

- no duplicate threshold constants inside v4 modules
- future UI and API work can read from one config source

### Workstream 3: Contract Lock

Before model or handler implementation, pin the concrete contracts already defined in `V4_ARCHITECTURE.md`.

**Required contracts**

- config loading pattern (`Settings` + `get_settings()`)
- command submission endpoint shape
- command history endpoint shape
- Socket.IO event names and payloads
- `commands` and `events` model fields
- v3 reuse boundary

**Expected result**

- Day 3-4 work no longer depends on guesswork
- frontend and backend can implement against the same contract

### Workstream 4: Persistence Foundation

Define the first persistent models:

- `Command`
- `Event`

Support only the minimum fields needed for:

- command request tracking
- retry tracking
- audit-ready event logging

**Expected result**

- DB schema direction is established
- later mission and operator tables can extend cleanly

### Workstream 5: Safe Command Path Skeleton

Define the first v4 command handling flow:

1. receive command request
2. run preflight check
3. reject unsafe command or persist command request
4. emit event record
5. call publish adapter hook

This can be stubbed behind interfaces if the full executor is not ready.

**Expected result**

- command path shape is locked early
- safety comes before transport
- hardware readiness failures are handled before command publish

### Workstream 6: Frontend v4 Shell

Create the v4 routed shell under `ui/src/v4/`.

**Target structure**

```text
ui/src/v4/
  AppShell.jsx
  routes.jsx
  pages/
    DashboardPage.jsx
    MissionsPage.jsx
    FleetPage.jsx
    CommandsPage.jsx
    SettingsPage.jsx
```

**Expected result**

- router and app-shell become real implementation, not just docs
- Socket.IO lifecycle can move into `AppShell`

### Workstream 7: `poc2` Hardware Command Bridge

Extend `poc2` beyond read-only telemetry so hardware can consume safe command intents.

**Initial scope**

- subscribe to `fleet/{drone_id}/command`
- parse at least `ARM` and `DISARM`
- translate accepted commands into MAVLink arm/disarm requests
- keep telemetry/status publishing behavior intact
- reject or ignore unsupported verbs until command coverage expands

**Expected result**

- the existing command publish path can reach real hardware through `poc2`
- end-to-end `ARM` / `DISARM` becomes possible after v4 or v3 emits MQTT commands
- `poc2` remains constrained and safety-first instead of becoming a full generic executor immediately
